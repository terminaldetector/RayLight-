## 2. Игровой контекст, который нужно сохранить

Направление проекта: **Half-Life × Descent × быстрый FPS / трёхмерный bullet hell**, с устройствами Granada.
Важны 6DOF, физические взаимодействия, видимые механические узлы, маневрирование и развитие вооружения.
GMod/GLua — текущая основная реализация. Нативный Source/HL2 — отдельная линия переноса.

PR #1 ввёл сокращённый обычный каталог: десять сменных модулей и два варианта мин.
Старые SWEP сохранены для совместимости, но не должны автоматически раздаваться лаунчером.
Ресурсы и приобретение оружия контролируются серверной логикой и прогрессией забега.
Четыре видимых крепления имеют собственные состояния; четыре независимых mouse-канала ещё не завершены.
Мины используют отдельный отсек и команду `+d6_mine`, стандартная клавиша — **C**.
Собственная сущность `d6_combat_drone` отделена от штатных сканеров Half-Life.

PR #2 добавил три слота саппортов: Призма, Створ, Клык, Кассета, Резонатор.
**G** активирует/отзывает саппорт, **T** переключает слот.
Активации расходуют конечные ячейки и энергию; смена модуля не должна пополнять запас.
Поддержаны взаимодействия устройств со своими снарядами, перехват и вынесенный подрыв.
Геометрия саппортов — процедурные прототипы; не объявлять её финальным анимированным арт-пакетом.

Игровые документы:

- `COMBAT_IMPLEMENTATION_RU.md` — бой, ресурсы, крепления и дальнейшие работы.
- `GRANADA_SUPPORTS_RU.md` — саппорты, поведение, визуальные прототипы.
- `DRONE_ART_TASK_RU.md` — художественное задание на обычные машины.
- `INSTALL_RU.md`, `MAPS_RU.md` — команды, карты и текущие различия runtime.

Лаунчер не должен реализовывать вторую прогрессию, дублировать ангар или менять боевую экономику.

## 3. Что известно о Windows-лаунчере

Пользователь ранее сообщил об отдельном агенте, который занимается Windows launcher.
Его исходный GUI-проект, архив или незапушенная рабочая копия в доступных источниках не найдены.
Поэтому текущая интеграционная поставка в `DRMD-6DOF/launcher/` — минимальный native Win32 EXE на Go stdlib.
Нельзя описывать её как завершение обнаруженного проекта другого агента: такой проект не был получен.
Если прежний код появится, перенести полезную интеграционную логику в согласованный основной лаунчер.
Не развивать две независимые системы установки с расходящимися форматами и путями.

Цепочка пользователя: **EXE → автоматическое обнаружение → ручное уточнение при необходимости → запуск**.
Интерфейс должен давать выбор runtime, карты и графического профиля без редактирования файлов вручную.
Для первого запуска нужен распакованный полный пакет; EXE не заменяет установленную Steam-игру.
Точные имена EXE, команд CLI и полей манифеста сверять с `launcher/README_RU.md` и исходниками поставки.

Текущий вход: `AbaddonLauncher.exe` в корне распакованного полного ZIP.
Окно построено через Win32; Python, Go, .NET и WebView на машине игрока не требуются.
`core.go` предоставляет `ValidateInstallation`, `DiscoverInstallations`, `LoadManifest`, `VerifyBundle`,
`InstallBundle`, `RollbackInstallation`, `ConfigureLaunch`. `main_windows.go` связывает их с GUI.
`abaddon-build.json`: `schema=1`, `project`, полный `revision`, `channel`, `payload_root`,
`files` с относительными `path`, `sha256`, `size`. Схема и пути валидируются до установки.
Настройки/журнал: `%LOCALAPPDATA%/AbaddonLauncher`; персональные файлы не уходят в сеть.
Ручной путь запускает именно выбранную копию. Steam `-applaunch` применяется только при совпадении
с установкой, обнаруженной по appmanifest. Две одновременные операции установки блокируются.

## 4. Два целевых режима

| Target | Установка | Что доступно |
|---|---|---|
| `gmod` | `descent_scanner` целиком в `garrysmod/addons/` | GLua-аддон: бой, полёт, HUD, саппорты, карты |
| `hl2-content` | Только `maps`, `models`, `materials` в выделенный каталог `hl2/custom/` | Проверка карт и контента штатным HL2; без GLua-боя и HUD |

Payload GMod находится в `DRMD-6DOF/descent_scanner/`, а не в корне репозитория.
`swep_construction_kit` — необязательный редактор; не устанавливать вторую копию при существующей.
Текущие игровые карты: `d6_city17_drain`, `d6_reactor_escape`, `d6_relay_vault`.
Для арены использовать `d6_relay_vault`; для начала эпизода — `d6_city17_drain`.
Совместимость BSP с настоящим HL2-клиентом требует отдельного запуска.

Режим `hl2-native` не следует показывать как установленный без собственного исполняемого payload.
В отдельной native-flight ветке runtime — Source SDK Base 2013 Singleplayer, Steam app **243730**.
Там есть исходный SDK overlay и flight lab; это не полный порт боевой системы Abaddon.

## 5. Обнаружение, установка и восстановление

Обнаружение должно учитывать Steam из реестра, дополнительные библиотеки и appmanifest игр.
Не фиксировать единственный путь `C:\Program Files (x86)\Steam`.
Ручной выбор должен принимать корректную папку игры, проверять её структуру и сохранять выбор.
При нескольких найденных установках показывать выбор; отсутствие игры не должно запускать чужой target.

Вся установка выполняется из одного версионированного payload.
Сначала проверить состав файлов, затем подготовить staging на том же файловом разделе назначения.
Рабочий каталог заменяется только после успешной подготовки; сбой должен сохранять прежнюю установку.
Предыдущую версию держать **вне `addons` / `custom`**, чтобы движок не смонтировал её второй раз.
Rollback возвращает предыдущий управляемый каталог, а не копирует старые файлы поверх новых.
Не удалять пользовательские сейвы, настройки, чужие аддоны или вручную изменённые каталоги вслепую.
Отличать собственную управляемую установку от совпавшего по имени чужого каталога.
При обновлении учитывать блокировки файлов запущенной игрой и сообщать понятную причину отказа.

Выбранный target, версия и назначение файлов должны быть видны до установки.
Игровые EXE запускаются с корректной рабочей папкой и экранированием путей с пробелами/кириллицей.
Не изменять глобальные Steam launch options и не сохранять ненужные личные пути в распространяемый пакет.
`autoexec.cfg`, `config.cfg`, пользовательские бинды и сохранения остаются под управлением пользователя.
Применение профиля — отдельный CFG и явный аргумент запуска, а не скрытая правка общих конфигов.

## 6. PBR, свет и тени: факты текущего кода

**Настоящего PBR в текущей сборке нет.** Не называть Phong, cubemap или настройку теней PBR-режимом.
Причина слабой реакции техники на свет лежит прежде всего в рендерере:

- `descent_scanner/lua/d6_art_render.lua`: материалы корпусов создаются через `UnlitGeneric`.
- `compile()` заранее окрашивает грани по фиксированной формуле нормали.
- `A.Draw()` использует один скаляр `render.GetLightColor(position)`, яркость ограничена снизу **0.56**.
- `RenderOverride` подменяет штатную модель процедурной сеткой; соответствие силуэта и тени не проверено.
- `entities/d6_combat_drone/init.lua` использует нейтральную модель `models/combine_scanner.mdl`.

В `materials/models/drmd/` — 31 VMT: базовые текстуры и tint, без phong/envmap/normal/roughness/metalness.
Генератор этих материалов: `tools/compile_models.py::write_materials()`; правки необходимо сохранять и там.
В `tools/build_episode.py::vault()` и VMF арены — 20 обычных источников `light`, lightmapscale 16.
Локальных `env_cubemap`, `shadow_control` и `env_projectedtexture` в этой арене нет.
У всех трёх текущих BSP есть LDR lighting, но HDR lighting и cubemap samples отсутствуют.
Запакованные `cubemapdefault.vtf` / `.hdr.vtf` не являются локальными reflection probes.

## 7. Разумные настройки текущего EXE

По умолчанию сохранять настройки игры. Графические профили применять по явному выбору.
В интерфейсе достаточно штатных теней, качества shadow texture и фильтрации текстур.
Материалы обозначать как **Source**, PBR — **не реализован**.

Пример сбалансированного CFG; итоговые параметры сверять с реализацией профиля:

```cfg
r_shadows 1
r_shadowrendertotexture 1
r_flashlightdepthtexture 1
r_flashlightdepthres 1024
mat_bumpmap 1
mat_specular 1
mat_forceaniso 8
```

Для повышенного качества достаточно shadow texture 2048 и anisotropic 16; не обещать улучшение всех объектов.
Эти настройки не добавят отсутствующие материалы, источники света или запечённые отражения.
Не включать `sv_cheats`, `mat_fullbright` и не форсировать HDR на LDR-картах.
Не запускать `buildcubemaps` автоматически на компьютере игрока.
`r_shadowrendertotexture` запрещён для Lua `RunConsoleCommand`; профиль исполнять обычным CFG при запуске.
При различиях версии движка сообщать о неподдержанном параметре, а не обходить ограничения.

## 8. Следующий графический шаг — в игровом коде

1. Исправить освещение процедурных корпусов с сохранением их анимированных узлов.
2. Проверить реальный силуэт тени дрона и саппорта, а не только наличие переключателя теней.
3. Подготовить материалы и cubemap probes арен, затем пересобрать и проверить BSP.
4. Если нужны локальные прожекторы, использовать небольшой бюджет `ProjectedTexture` и замерять кадр.

Простая замена `UnlitGeneric` на `VertexLitGeneric` недостаточна: IMesh требует корректного lighting state.
Массовое удаление `DrawShadow(false)` у снарядов/служебных объектов также не является исправлением.
В GMod исходная общая квота — восемь projected textures с тенями, включая фонарик игрока.
Каждый дополнительный источник с тенями увеличивает стоимость рендеринга; не повышать квоту без замера.

## 9. Проверки и оставшиеся границы

Сегодня выполнены **326 исходных Lua-проверок** объединённых PR.
Проверен комплект игровых ресурсов: **3 BSP и 79 MDL** с сопутствующими файлами.
Это проверки логики/состава; они не заменяют настоящий графический запуск.
Запуск GMod/HL2-клиентов и визуальная проверка арен пока не выполнены.
EXE скомпилирован для `windows/amd64` стандартным Go toolchain, без внешних Go-зависимостей.
12 групп тестов установщика прошли на Linux: VDF/Unicode, нормализация пути, manifest/path traversal,
повреждение и отсутствие source, сохранение пользовательских файлов, stale managed files, HL2 filtering,
rollback, symlink/reparse rejection, незавершённая транзакция, блокировка параллельной операции,
восстановление после ошибки второго rename, точные аргументы запуска и защита отдельного CFG.
На Windows те же тесты, native build и реальный Win32 `--smoke-ui` успешно прошли в
[CI run 44942885052](https://github.com/terminaldetector/RayLight-/actions/runs/44942885052)
на commit `2a97e14b93d7c8bac5ef91eaa80649c92ccb0d2a`. После него уточнён только этот документ.
Окно было создано и закрыто с проверкой наличия контролов; это не интерактивный игровой прогон.
В режиме `--smoke-ui` установка/откат/запуск заблокированы, настройки изолированы во временной папке.

Минимальный следующий прогон: первый запуск EXE, другая Steam library, ручной путь, установка и запуск карты.
Затем одно обновление/rollback с сохранением пользовательских файлов и проверка выбранного графического профиля.
Не повторять полный игровой аудит ради изменения UI лаунчера; проверять изменённый механизм и его границы.
